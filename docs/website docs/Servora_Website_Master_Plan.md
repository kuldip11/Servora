SERVORA — WEBSITE MASTER PLAN
Public Website • Information Architecture • Content • SEO • Performance • Support
Purpose: Define the complete public-facing website for Servora before implementation. The website should communicate the product clearly, build trust, support discovery through search, perform extremely well, and provide strong paths into the application and customer support.
## 1. Website Goals
- Present Servora as a polished, credible restaurant/POS platform rather than simply a software dashboard.
- Explain what Servora does, who it is for, and why it is valuable within the first few seconds.
- Create clear conversion paths: Start / Get Started, Book a Demo, Sign In, Contact Sales, and Contact Support.
- Demonstrate the complete product surface: restaurant operations, orders, menus, kitchen, staff, inventory, billing, customer ordering, analytics, and administration.
- Make product capabilities understandable to restaurant owners and operational teams without requiring technical knowledge.
- Build organic search visibility with dedicated, useful pages rather than keyword-stuffed copy.
- Prioritize excellent Core Web Vitals, fast navigation, accessible UI, responsive layouts, and minimal client-side JavaScript.
- Create a support and trust layer that makes the product feel dependable for a business-critical workflow.
## 2. Primary Audience
- Restaurant owners and operators.
- Restaurant managers and administrators.
- Front-of-house staff, waiters, and cashiers.
- Kitchen teams and kitchen managers.
- Multi-branch restaurant groups.
- Businesses evaluating POS and restaurant-management software.
- Customers interacting with restaurant QR ordering.

## 26. SEO Strategy
- Create a unique title and meta description for every indexable page.
- Use one clear H1 per page and logical H2/H3 hierarchy.
- Build topic clusters around restaurant POS, restaurant operations, QR ordering, kitchen management, menu management, inventory, billing, and multi-branch operations.
- Create useful feature pages rather than stuffing keywords into the homepage.
- Use descriptive, stable URLs.
- Add canonical URLs.
- Generate XML sitemap.
- Configure robots.txt intentionally.
- Use Open Graph and social metadata.
- Use structured data where genuinely applicable, such as Organization, SoftwareApplication, WebSite, BreadcrumbList, FAQPage only where the visible page content qualifies.
- Add internal links between related features, solutions, guides, FAQs, and conversion pages.
- Use descriptive image alt text.
- Avoid duplicate pages created solely for SEO.
- Avoid unsupported review/rating/schema claims.
- Ensure authenticated app pages are not accidentally indexed.

## 28. Performance Requirements
- Prefer server-rendered/static content for marketing pages where the framework supports it.
- Keep JavaScript minimal on content-heavy pages.
- Optimize screenshots and product media.
- Use modern responsive image formats and correct dimensions.
- Lazy-load below-the-fold media.
- Avoid large third-party scripts unless their business value is clear.
- Avoid unnecessary animation libraries.
- Use lightweight transitions and respect reduced-motion preferences.
- Preload only truly critical resources.
- Use caching/CDN delivery appropriately.
- Prevent layout shift by reserving media dimensions.
- Keep fonts limited and optimized.
- Measure real performance rather than assuming it.
## 29. Accessibility

## 34. Content Rules
- Write for restaurant operators first; technical details belong on technical/support pages.
- Use specific outcomes instead of vague marketing language.
- Show, then explain: screenshots and workflows should support claims.
- Never claim an integration, feature, certification, uptime percentage, customer count, review score, or security standard unless verified.
- Keep terminology consistent across website and application.
- Avoid duplicate copy across feature pages.
- Use short paragraphs, scannable headings, bullets, diagrams, and contextual CTAs.

## 39. Definition of Done
The website is complete when it can function as the public face of Servora: a visitor can discover it through search, understand the product without assistance, find the feature or solution relevant to them, verify trust and support information, compare or understand pricing, contact the team or start onboarding, and move into the application without confusing transitions. The site must remain fast, accessible, maintainable, and factually aligned with the actual Servora product.
## 40. Important Product-Accuracy Rule
This document defines the website information architecture and content requirements. Before publishing any specific technical claim, integration, pricing detail, compliance/security statement, performance number, customer statistic, or workflow promise, verify it against the current Servora implementation and approved business information. The website must describe the real product, not an assumed future version.
